# Google Drive and iCloud Drive backup implementation plan

Status: **Implementation started; cloud backup is not ready for release.** The archive foundation and a Windows manual Google Drive flow are in source, but need provider setup and real-account testing. Android, iCloud and migration remain. Prepared 2026-11-06. The owner selected Google Drive on Windows and Android, iCloud on iOS, provider account protection without a separate backup password, and replacement of Supabase sync only after migration. This document is the authoritative plan for this request; existing plans in `IMPLEMENTATION.md` remain unchanged.

## Outcome and recommendation

Replace the need for Supabase for **backup and recovery** with opt-in snapshots in the user's own Google Drive or iCloud Drive account. A user can create a backup, see its date and status, and restore a chosen backup after reinstalling or moving to another supported device. Keep local notes usable without an account or network connection, and retain manual ZIP export/import.

This is feasible, but a periodic backup is not the current Supabase feature's live, two-way note sync. An edit on one device will not automatically appear in an already populated library on another device. Restoring a snapshot is a deliberate action; independent edits on multiple devices must not silently overwrite each other. If live multi-device sync is required, design and approve it separately before removing the existing sync feature.

**Proposed first release:** Google Drive backup on Windows and Android; iCloud Drive backup on iOS. Google Drive on iOS can be added after the shared Google identity and restore flow are proven. Windows iCloud is a user-selected synced folder/manual file workflow, not direct access to the iOS app's iCloud container. Web support is deferred until its authentication, storage, and browser constraints are evaluated. Android and iOS are currently unverified platforms in this checkout.

| Destination | Proposed access | Recovery and limits |
| --- | --- | --- |
| Google Drive | Drive API `appDataFolder`, with the `drive.appdata` scope and the user's Google account. | Hidden app-owned files, not ordinary visible Drive files or WhatsApp's backup listing. Verify that the chosen Google Cloud project and client registrations allow the intended Windows/Android/iOS builds to discover the same app data. |
| iCloud Drive | Native iOS ubiquity container with iCloud Documents entitlement and a Flutter platform bridge. | Apple Account, iCloud Drive, signed app and configured container required. Transfer is managed by iCloud; local file creation does not prove the upload finished. |
| Existing synced folder | Windows desktop automatic backups can already target a user-selected folder, including a Drive for desktop or iCloud Drive folder if installed and available. | A practical manual alternative today, subject to the existing archive limitations below and the external sync client's status. Folder access and cloud upload are not guaranteed by BetterNotes. |

The provider accounts and storage are separate. A Google backup will not appear automatically in iCloud, or vice versa. For Android-to-iOS migration, use Google Drive on both platforms once supported, or transfer an exported ZIP using the system file/share picker. Do not promise automatic cross-provider recovery.

## Current project and gaps

- `lib/data/local_store.dart` stores notes, images, settings and revisions. The active library is filtered by `ownerId`; `NotesController.ownerId` in `lib/state/notes_controller.dart` currently depends on Supabase authentication. Signing out and `clearOwner` have data consequences that must be understood before changing account handling.
- `lib/data/backup.dart` builds a validated ZIP with current-owner notes, referenced images, and retained history; it normalizes the exported owner. `NotesController.exportBackup()` flushes open editors and serializes its operation through the controller. Reuse these boundaries and existing archive validation rather than copy the database file or add a parallel note model.
- The archive includes the original appearance preferences plus `libraryOptions`, `savedFilters`, `imageQuality`, and `alwaysShowNoteHeader`. Automatic Trash retention is excluded to avoid enabling automatic deletion on the receiving device. Review other settings, including `stickyImported` and platform-specific preferences. `openNoteWindows`, folder paths, credentials, account IDs, task registration, hotkeys, status/error fields, and device-specific integrations must not be blindly restored to a different device.
- Backup is currently limited to 128 MiB overall, 5,000 notes, 10,000 assets, 16 MiB of note JSON and 8 MiB per image. Missing images and history that exceeds the applicable limits now fail export. These limits constrain any promise of backing up everything; make the size policy explicit and visible.
- `BackupData.importInto` deliberately imports notes as copies with new IDs, clears expired reminders, and restores selected preferences only when asked. `LocalStore.importCollection` is transactional. Repeated imports therefore create duplicates; this is safe for manual imports but needs an explicit cloud recovery experience.
- `lib/data/auto_backup_io.dart` writes timestamped files and prunes old backups on desktop; `auto_backup.dart` selects a web stub, and its IO implementation enables desktop only. `settings_page.dart` exposes export/import and folder backup. Existing file export/import works through platform save/share and file selection APIs; actual mobile behavior needs device testing.
- `lib/data/cloud_sync.dart`, Supabase initialization in `lib/main.dart`, sign-in and realtime/polling in `notes_controller.dart` and `settings_page.dart` provide a separate revision-based sync system. `pubspec.yaml` still depends on `supabase_flutter`. Current project status says the owner's Supabase configuration is absent, not that no user can have existing account-owned data.

## Proposed backup contract

1. Include all current, archived and trashed notes belonging to the selected local library, rich text, drawings, note metadata, reminders, referenced images, and all retained note history, subject to a documented, tested size policy. Inventory serialized `Note` fields and revision-only images during implementation. Fail with an actionable explanation if required data is unavailable; offer a clearly labelled partial export only if the owner later approves it.
2. Define a versioned, validated preference allowlist for portable appearance, editor and library preferences and saved filters. Keep machine-specific paths, credentials, provider tokens, transient errors, OS registrations and device session/window state local. When a setting has side effects, apply it through the appropriate controller/OS integration or leave it off and tell the user. Recreate only future eligible reminders after a restore; never fire past or duplicate reminders automatically.
3. Evolve the archive schema and reader without breaking existing v1/v2 ZIP imports. Before increasing the 128 MiB limit, measure memory and performance on target devices, set realistic bounded limits, and test hostile/truncated archives. If a complete archive exceeds supported limits, report failure with next steps; do not silently omit history or claim success.
4. Snapshot a consistent library: flush editors, serialize against writes, and ensure the account/library cannot change mid-export. Never publish a snapshot if referenced data is missing or validation fails. After creating the backup, verify the uploaded object or download and validate it before reporting cloud success; provider-specific status must describe what is actually confirmed.
5. Archives are currently readable ZIPs. Provider account protections and transport security are not the same as BetterNotes end-to-end encryption. Label this clearly. Do not claim WhatsApp-equivalent encryption. Optional client-side encryption, password/key recovery and recovery testing require a separate design decision; never put a recovery key or access token in the archive or logs.

## Provider design and lifecycle

Use a small backup destination interface only where needed: connect/disconnect, list snapshots, upload, download, delete and report status. Keep archive creation/validation independent of authentication and provider SDKs. Each snapshot has a unique ID, creation time, originating device label, archive schema, byte size and a checksum; treat provider metadata as untrusted and validate the archive itself. List by account and device, never assume the newest timestamp is authoritative, and handle pagination.

**Google Drive:** set up a Google Cloud project, Drive API, OAuth consent and supported OAuth client registrations for each platform and release signing identity. Use the least-privilege `drive.appdata` scope for storage, plus `openid email` only to show which account is signed in; do not embed a confidential client secret in an app. Confirm the actual Dart/Flutter authentication and Drive API libraries, platform support, token refresh, desktop browser redirect/PKCE, lifecycle and dependency maintenance in a small proof of concept before selecting packages. Store tokens through platform-supported secure mechanisms, never in backup ZIPs or logs. Upload a new uniquely named object, complete and verify it, then make it eligible for listing; retain prior verified snapshots if upload, verification, quota or network fails. The app data folder is hidden, has special deletion restrictions and can be removed by the user or by uninstalling the app from My Drive; it is separate from Google's device-backup folder. Verify account and OAuth-project identity across installations before promising cross-device access.

`lib/data/google_drive_backup.dart` implements upload, verification, listing and validated download using an injected authenticated HTTP client and Google's Drive API package. It keeps new snapshots pending until downloaded and checked, deletes its own unfinished file when a transfer fails, and offers `discardPending()`, which removes pending files older than 15 minutes so an in-progress upload from another device is left alone. `lib/data/google_drive_auth_io.dart` starts a Windows browser sign-in with a loopback callback, PKCE, a state check and the `openid email` scopes used only to name the signed-in account. Interactive credentials stay in memory for that screen; only when the person enables the daily schedule is a refresh token written to platform secure storage, and Disconnect removes it. `lib/data/google_drive_account.dart` reads that email for display and treats any failure as an unnamed account, never as a failed backup. `lib/ui/google_drive_backup_page.dart` supports manual upload, listing, unfinished-upload cleanup and import as copies, with distinct messages for denied consent, timeout, network, integrity and not-configured failures. After a verified upload it keeps the newest three snapshots for this device and deletes that device's older ones, reporting any delete it could not perform; other devices' snapshots are never pruned. An opt-in daily automatic backup reuses a refresh token saved in platform secure storage (`lib/data/google_drive_session.dart`) and runs while the app is open; the token is created only when the person enables that switch, and Disconnect forgets it. Snapshots are labelled with the machine's hostname. Simulated tests cover consent denial, callback validation, cancellation, verified publication, corruption, pagination, malformed metadata, unfinished-upload cleanup, per-device retention, refresh-token exchange, account lookup and the automatic schedule. Real OAuth, Drive behavior, secure-storage behavior and cross-client access are unverified.

### Owner setup for a Windows test build

1. In [Google Cloud Console](https://console.cloud.google.com/), create or select the intended project and enable the Google Drive API. Configure the OAuth consent screen and its audience; while the app is in testing, add the Google accounts that will test it. Complete any Google verification required before broader release.
2. Create an OAuth client of type **Desktop app** in that project. The client ID is public configuration; do not put an access token, refresh token or client secret in the repository or chat. Use the same Google project for future Android client registrations, then verify cross-platform app-data visibility with real accounts.
3. Build or run Windows with the public client ID: `flutter run -d windows --dart-define=GOOGLE_DRIVE_DESKTOP_CLIENT_ID=<desktop-client-id>`. Without that define the screen reports that Drive is not configured. Use the normal installed Flutter command for this project. No automatic backup runs; the user must connect and choose **Back up now**.
4. On a test account, create a representative backup, verify it appears, close and reconnect, then import it into a separate test library and compare notes, images, history and selected preferences. Test denial, cancellation, offline behavior and wrong accounts. These steps are pending and must not be treated as completed.

The current desktop flow has not been verified against an actual Google OAuth client. An Apple Developer membership, stable app identifier, iCloud Documents entitlement and container must be configured separately on a Mac before iOS integration can be built and tested.

**iCloud Drive:** configure Apple Developer signing, a stable bundle identifier, iCloud Documents capability and a stable ubiquity container. The current iOS project has no iCloud entitlement configured. Use a small Swift platform channel or a maintained dependency only after checking platform compatibility. Access container URLs off the main thread, use Apple's coordinated file access, detect account/container changes, enumerate metadata, request downloads and handle files that are not local. Create unique snapshots rather than overwriting a shared file. Distinguish **saved locally / waiting for iCloud** from **uploaded** using available ubiquity status and errors; confirm behavior on real devices before promising remote durability. Handle iCloud conflicts, unavailable account, quota, revoked access and delayed downloads without removing a previous good snapshot.

**Retention and concurrent devices:** the newest **3 verified snapshots per device** are kept. After each manual upload is verified, `pruneDevice()` deletes that device's older verified snapshots and reports any it could not delete; it never prunes another device's snapshots. Unique device and snapshot IDs, not timestamps alone, identify snapshots, and there is no shared mutable latest file. A reinstall may create a new device ID (the current label is the machine hostname), so surface orphaned histories and provide explicit user-managed deletion. Account/provider switching must show which destination is active and must never delete data as a side effect.

**Scheduling:** offer Back up now plus an opt-in automatic schedule, proposed daily while the app is running/foregrounded and after pending changes have been saved. On Windows this is implemented: enabling **Back up automatically once a day** saves the Google refresh token in platform secure storage (on Windows an AES-GCM value whose key is held by Windows Credential Manager) and runs a due check every 30 minutes, 45 seconds after startup and 5 seconds after enabling. Uploads are verified and pruned exactly like manual ones, and failures are recorded for the About diagnostics and the Drive screen. Nothing runs while the app is closed. On Android, investigate WorkManager only if background backup is required; it offers deferred scheduling, not an exact daily time, and must safely coordinate with the app database and token refresh. On iOS, system background execution and iCloud transfer timing are not guaranteed; initially retry when the app next opens and report pending uploads. No claim of guaranteed backup when the app is closed, offline, force-stopped or the OS restricts work.

## Restore and Supabase transition

1. Let the user connect the intended provider/account and inspect dated snapshots with device name, size, status and counts after validation. Do not overwrite the local library automatically when sign-in or app launch finds a backup.
2. Offer **Import as copies** using the existing import semantics. For a newly installed empty local library, offer a distinct **Restore library** flow after validating the full download. For a nonempty library, preserve data with a local safety ZIP and explicit confirmation before any replacement; first define and test an atomic transaction or recoverable staged swap that covers notes, images, revisions and portable settings. If the safety backup or preflight fails, stop without changing the library. No implicit merging or last-writer-wins replacement.
3. Reconcile active editors and Windows child windows before restore; serialize writes, clear stale view state, reload controllers and reschedule eligible reminders only after a successful commit. Repeated selection of the same backup must not silently add duplicates: show the prior restore/import and ask the user to choose deliberately. On interruption or validation failure, leave the existing library and last verified cloud snapshot usable.
4. Before removing Supabase, audit every owner partition and image: active, guest and previously signed-in owners, dirty notes, local and remotely stored images, revisions and deleted notes. Provide a non-destructive migration that flushes/syncs where possible, downloads and verifies required missing assets, exports a restorable local safety ZIP, and preserves the old state until a replacement backup and restore have been verified. Never call `clearOwner`, sign out, or drop the dependency as a migration shortcut. If the remote service is unavailable or a prior owner's data cannot be accessed, stop and explain what remains unavailable. Account-owned and guest libraries must not be silently combined or hidden.
5. Only after migration is tested and the owner accepts losing live sync, remove or disable Supabase configuration, authentication, polling/realtime, cloud asset retrieval, UI and dependency in a separate deliberate stage. Retain a rollback path: old release plus untouched local safety export; do not delete remote data or change the Supabase project automatically. If live sync remains a requirement, keep it while developing this backup feature.

## Stages and acceptance checks

- [ ] **Resolve remaining scope:** the owner selected the platforms, provider protection, and replacement of live sync after migration. Confirm remaining data/settings exclusions, retention, and recovery of existing Supabase data.
- [ ] **Archive and safe recovery:** inventory fields and settings, implement a backward-compatible schema and honest completeness reporting, define tested size bounds, and build a validated restore into a fresh library. Test formatted notes, inline and attached images, drawings, archive/trash, future/expired reminders, history-only images, portable preferences and old ZIP versions. Missing data, malformed input, oversize files and interrupted restore must leave local data intact. Test repeat imports and recovery of a safety ZIP.
- [ ] **Google vertical slice:** on one supported device, sign in, back up a real representative library, verify the uploaded copy, then restore on a fresh installation using the same account. Cover wrong account, denied consent, expired token, offline/retry, quota, interrupted upload and more than one snapshot. Confirm actual OAuth app-data access across Windows and Android clients in the same project; do not assume it.
- [ ] **Google desktop and Android:** implement accessible settings/status and opt-in schedule, exercise app restart, credential refresh, cancellation, concurrent devices and retention. Verify Windows and Android builds and real-device transfer in both supported directions. If a background scheduler is added, test storage contention and background restrictions independently.
- [ ] **iCloud iOS slice:** on a signed physical iOS device, enable the configured container, create and confirm a remote backup, and restore on a second device or fresh install with the same Apple Account. Test pending upload versus completed upload, a download not present locally, unavailable iCloud, quota, account changes, conflicts and interrupted restore. Validate entitlements and signing in Xcode.
- [ ] **Migration and rollout:** run the Supabase data inventory and migration cases above, including offline and missing-image failure; verify rollback, retention and old ZIP compatibility. Update `README.md`, `docs/USER_GUIDE.md` and `STATUS.md` to match the shipped behavior. Remove Supabase only after the transition acceptance criteria are met.

For implementation, format changed Dart files, run static analysis once after related changes, run meaningful archive/controller/provider tests and the relevant existing backup tests (`test/auto_backup_test.dart`, `test/backup_browser_test.dart`), then build and exercise each affected platform. Real provider accounts and devices are needed to establish end-to-end recovery; mocks alone cannot establish OAuth, iCloud transfer, or background behavior. Android SDK and a Mac with Xcode, signing and an Apple Developer account are prerequisites noted by the project; their current availability has not been rechecked for this planning task.
